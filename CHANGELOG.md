## Unreleased

### Bug Fixes
- `PruneCallback` now re-points `learn.opt` at the model's live parameters after every prune. Structured pruning replaces the `nn.Parameter` objects of the layers it shrinks, and the optimizer `Learner.fit` built still referenced the old ones: on a small convolutional model the optimizer held 1 of the model's 10 parameters after the first prune, and the pruned layers' weights did not change again for the rest of the fit (max |ΔW| = 0.0 over the following epoch). The optimizer object itself is kept and its parameter groups are rewritten in place — fastai binds `opt.step` before the `before_step` event where the prune runs, so a freshly built optimizer would not be the one that steps that batch — which keeps the groups, the hypers and the scheduled learning rate of the batch being stepped. The optimizer state of a parameter the prune spared is kept; the state of a replaced parameter is dropped, along with the dead parameter that keyed it

## 0.4.0

### New Features
- `FakeQuantizer(model, weight_bits=4, act_bits=8)` rounds weights and activations onto the widths asked for **in floating point**, doing the arithmetic itself, so any width pair can be asked for on any model wherever that model already runs. It follows the shape of its siblings: the model at construction, `qscheme` for the scale axis (`per_tensor`, `per_channel`, `per_group`), `symmetric`, `group_size`, `observer`, the per-layer `layer_bits` and `layer_act_bits` dicts beside the defaults, mutation in place, and `print_precision()` as the report. `calibrate()` observes the activation ranges and takes a fastai `DataLoaders` or one of its loaders, refusing anything else by name; `quantize_model()` rounds in place and returns the same model; `remove()` puts the floating-point weights back bit for bit. `None` leaves a tensor in floating point, `16` is a real 16-bit grid, and `observer='dynamic'` recomputes activation scales per batch instead of freezing them. `FakeQuantSpec` and `fake_quant_spec(model)` carry the provenance. The model keeps its floating-point dtype and its ordinary modules, so this measures what a width costs in **accuracy**, not what it saves: a floating-point copy of every rounded weight is held, biases stay in floating point where an integer kernel would carry them at int32, BatchNorm is not folded, and a rounded model is not a QAT model. `Quantizer`, the precision table and the ONNX exporter are untouched — this ships beside them
- `FakeQuantizeCallback` trains a model through `FakeQuantizer`'s rounding — `learn.fit(5, cbs=[FakeQuantizeCallback(weight_bits=4, act_bits=8)])` — taking the same grammar arguments as the quantizer it drives, plus `freeze_act_pct`, `act_averaging` and `model`, and exposing that quantizer as `self.fake_quantizer`. `before_fit` registers a weight parametrization on every layer with a width and installs the activation observers, so the weights are rounded at every forward and the straight-through gradient reaches the floating-point master the fastai optimizer already holds; activation ranges are observed with a moving average over training batches only and frozen at `freeze_act_pct` of the fit or at its end; `after_fit` bakes the rounded weights into ordinary parameters, leaving the model in the state `quantize_model()` leaves, and `bake()` and `strip()` are public so a fit that raised can still be finished or unwound. The model keeps its floating-point dtype: it is not smaller and not faster, and measured on ResNet-18 on one GPU, single run, the fit cost about 1.17× the step time and roughly 120 MiB more peak memory. While a parametrization is live `m.weight` is computed, so a write to it lands nowhere: six readers were corrected — `Sparsifier`'s mask application, its lottery-ticket rewind, its weight snapshot and its sparsity report, and both criteria paths — and `Pruner` refuses a parametrized model by name
- `FakeQuantizeCallback(weight_bits=4, weight_schedule=lin, weight_widths=(16, 8, 4))` lowers the width the model trains at through a ladder of rungs, coarsest first, ending at the width the callback was already asked for. Any fasterai `Schedule` selects the rung and `current_widths` reads back the pair the model is rounding at right now; `act_schedule` and `act_widths` drive the activation side on their own timing, or not at all. The last training batch is detected explicitly rather than derived from progress, because `pct_train` is incremented after each batch and so never reaches 1.0 inside `before_batch`, and `bake()` sets the final rung too, so a fit cut short by an exception or a `CancelFit` does not bake a width the provenance does not name. A layer whose width was named by `layer_bits` or `layer_act_bits` is excluded from the ladder by name, resolved once at `before_fit`, rather than silently overwritten. `FakeQuantSpec` records the ladders that were **asked for**, not the rungs a given fit had time to visit, so a model that arrived at 4 bits through one is distinguishable from a model trained at 4 bits throughout. Whether lowering the width progressively is worth doing is not measured here
- `export_qdq(model, sample, path, activation_dtype='uint8')` writes the **activation** Q/DQ pairs of the exported file as `uint8` with a zero-point of 128 and the same scales, for consumers that read unsigned activations; the weight pairs stay `int8` per-channel. The rewrite is checked rather than trusted: every `QuantizeLinear` must come back carrying a uint8 zero-point of 128 and none may read a graph constant, every `DequantizeLinear` fed by one of them must carry the same and every other one must still be int8, the file is run against the graph as produced and must be output-for-output identical (the produced file saturates to the full int8 range, so shifting the whole range by 128 is a bijection), and it must load and run at the default optimization level. A model recorded with `symmetric=False`, a `QuantizeLinear` whose output is read by anything but a `DequantizeLinear` or exposed as a graph output, and a zero-point that is not a graph constant are each refused by name, and nothing is kept on disk — the sidecar included. The default (`'int8'`) is unaffected, and a consumer that only accepts a zero-point of 0 (TensorRT among them) wants that default
- `Quantizer(backend='pt2e', skip_activations=['features.0'])` leaves the activations a named module produces in **floating point**, a second axis of the precision grammar next to `qdq_placement`. A name selects the nodes torch attributes to that module or to anything under it; for each of them the output qspec, every consumer's entry for it and every spec defined against a cleared edge are removed, so the tensor and every edge reading it stay in the model's float dtype while the module's weights and its input stay INT8. Name the block, not the convolution: the observer of a fused conv→BN→ReLU partition sits on one node of the partition, and a name nothing observes is refused with the name to use instead. The pass edits the graph torch has just annotated, so the prepared model, a QAT run and the exported file all carry it, and it composes with `skip_conv_add` in either order. Why it exists: torchvision `mobilenet_v3_small` under pt2e static INT8 collapses to 0.8 % top-1 (n = 500, one calibration draw) because one activation site, the stem block's output after BN folding, spans two orders of magnitude across channels and a per-tensor step zero-codes the small ones; leaving that site in floating point restores 65.8 % on the symmetric grid, the same as per-channel INT8 at that site. The consuming convolution then reads a floating-point input and is not fused into an INT8 op by a runtime: an accuracy lever whose cost in latency is that runtime's property, unmeasured here. `QuantSpec.skip_activations` and `PrecisionCell.skips_activations` record it, so `as_dict()` carries one more key; old pickles keep loading
- `Quantizer(backend='pt2e', qdq_placement='skip_conv_add')` names **where the Q/DQ pairs sit**, a new axis of the precision grammar. It leaves one edge of every residual block unquantized — the addend produced by a single-user convolution partition — so that result reaches its addition at accumulator precision instead of being rounded to INT8 first. The pass edits the graph torch has just ANNOTATED, so the placement the caller asked for is the one the prepared model, a QAT training run and the exported file all carry; QAT trains through it with `Quantizer(backend='pt2e', method='qat', qdq_placement='skip_conv_add')`. A placement that matches nothing raises rather than being recorded as applied, `qdq_stats` reports the edges as `n_unquantized_conv_add`, and `export_qdq` refuses (keeping no file) a graph that contradicts the placement the model records. The option is **opt-in and changes the arithmetic**: post-training, every pair the graph keeps carries the scale it would have had, but the effect on a trained model's accuracy is unmeasured, and what a runtime does with the resulting graph is that runtime's property. The default, `'per_op'`, is byte-for-byte what this backend has always produced
- `Quantizer(backend='torchao', weight_bits={layer: 8|16}, act_bits=16)` applies a per-layer width over the `nn.Linear` layers torchao rewrites, so part of a Linear-heavy model can be held in floating point. Naming every layer `8` produces the same artifact, byte for byte, as the uniform `method='int8_weight_only'` recipe
- `QuantizeCallback(backend='pt2e')` runs quantization-aware training through the pt2e flow: `before_fit` captures the model with `torch.export` on a batch from `learn.dls` and calls `prepare_qat_pt2e` with the same symmetric int8 scheme as the PTQ path, but with fused fake-quantize and moving-average observers so the gradients see the rounding; `after_fit` calls `convert_pt2e` and the converted model carries its `QuantSpec`. An exported graph refuses `.train()` and `.eval()`, which fastai's `TrainEvalCallback` calls on every fit and validate, so the callback binds working replacements on the instance, and a static-batch preflight replaces what used to be a full training epoch followed by a mid-validation crash. The callback also rebuilds the optimizer after it swaps the model in — `Learner.fit` builds the optimizer before `before_fit` runs — preserving `fit()`'s hypers and fastai's per-parameter no-wd and force-train marks across the rebuild; without that transfer, BatchNorm parameters and biases silently start receiving weight decay on the pt2e path, and a `qconfig_mapping` built on learnable fake-quant adds trainable scale and zero-point parameters the pre-built optimizer never held
- `Quantizer` gained a precision grammar: the keyword-only `weight_bits`, `act_bits`, `qscheme`, `group_size` and `symmetric`, resolved once and validated against `fasterai.core.precision.PRECISION_SUPPORT`, the capability matrix naming which backend supports which width, scale axis and symmetry. The matrix is code, not prose — the documentation table is rendered from it, the resolver validates against it, and a test cross-checks every legacy cell against `torch.ao`'s own `get_default_qconfig` so it cannot drift. The resolved request is a frozen `QuantSpec` attached to the quantized model and readable with `quant_spec(model)`; the exporter reads it to refuse an export it cannot write faithfully, naming the cell (opset 18 has no int4 Q/DQ, and a weight-only W8A16 model has no activation pairs to write). Every call that predates the grammar is byte-identical, state_dict tensors and exported ONNX included
- `Quantizer(backend='pt2e')` captures the model with `torch.export` and runs `prepare_pt2e`/`convert_pt2e` under a symmetric int8 configuration — per-tensor symmetric activations clamped to `[-127, 127]` with the zero-point pinned to 0, per-channel symmetric weights on `ch_axis=0` — so an int8 model can be handed to a runtime that consumes explicit Q/DQ graphs instead of staying a PyTorch-only artifact. `export_qdq(model, sample, path)` writes it as an ONNX file that keeps its Q/DQ nodes, which the optimizer pass behind `export_onnx` strips; `qdq_stats(path)` counts the Quantize and Dequantize nodes, detects per-channel by scale shape and audits non-zero zero-points; `verify_qdq(model, path, sample)` reports argmax agreement between the PyTorch model and the exported graph and refuses a sample that does not split into equal batches, which a static-batch graph rejects. `onnx` and `onnxscript` stay optional and are gated at call time. `dynamic_batch=True` cannot produce a dynamic axis on a pt2e graph on the torch versions tested, and warns explicitly instead of silently emitting a static one

### Breaking Changes
- **Every compression ratio is a fraction in [0, 1]**: `sparsity=0.5`, `pruning_ratio=0.3`. `sparsity` used to be a percent, and `pruning_ratio` accepted a fraction or a percent and guessed with a `> 1 → /100` heuristic — so `sparsify_model(0.5)` meant half a percent, `Pruner(m, 1)` meant everything and pruned nothing, and `sparsify_model(True)` was accepted. One converter, `fasterai.core.ratio.as_fraction`, is now the only place a value is interpreted, and every entry point calls it: torch-pruning receives the fraction as is, and no other `/100` remains in the library. A value in (1, 100] emits a `FutureWarning` naming the fraction to pass and is divided by 100, once, at the call the user wrote, **for one release**; values outside [0, 100] raise, a scalar pruning ratio of 0 raises, a per-layer dict value of 0 leaves that layer alone, and non-numbers raise `TypeError`. The sensitivity API, since moved out, was renamed at the same time. Printed reports and logs keep their percent formatting: they are display, not API
- Sensitivity analysis (`analyze_sensitivity`, `SensitivityAnalyzer`, `SensitivityResult`, `LayerSensitivity`) is no longer part of fasterai: it moved to the higher-level FasterAI workflow package. Importing any of the four names from `fasterai.analyze.sensitivity` now raises an `ImportError` that names where they went, instead of a bare `AttributeError`; the module itself still imports, and `import fasterai` is unaffected. fasterai holds the compression *mechanisms* — a per-layer sweep that ranks layers against each other is allocation guidance, and it belongs one level up
- `Quantizer.quantize` now raises when a backend fails, instead of printing `Error during quantization: ...` and returning the model it was given. Its outer `except Exception`, and the same catch-all inside the dynamic path, meant a failed call handed back the original float model with a line that scrolls past in a notebook; on the dynamic path the returned model was then tagged, so an unquantized model carried a quantized model's provenance. The error names the backend and the method and is chained to the cause the backend raised. The per-channel to per-tensor retry is unaffected: it is a recovery, records `qscheme='per_tensor'` on the spec, and is now covered by a test
- `Quantizer.quantize(device=...)` now raises `ValueError` unless the device is a CPU. PyTorch quantization converts on the CPU: `device='cuda'` used to calibrate on the GPU and return a graph whose scales sat on `cuda:0` while its weights sat on `cpu` — tagged as quantized, and raising `Expected all tensors to be on the same device` on the first input it was given. The argument is kept so `device='cpu'` callers are unaffected
- `Quantizer` now refuses a conversion that produced no integer weight at all, instead of tagging the result. On `method='dynamic'` the post-condition is the one that suits that flow: at least one `nn.Linear`/`nn.LSTM`/`nn.GRU` present in the source must come back integer-weighted. A model holding none of them (a convolutional network) and an `nn.RNN` model — `nn.RNN` is in the qconfig spec but in no dynamic mapping torch ships, so it is never rewritten — both used to come back in floating point tagged `W8A8`, and now raise naming the types that flow rewrites
- `Quantizer` now refuses a model with more than one convolution when the backend rewrote none of them, instead of returning it with only its `nn.Linear` layers quantized and a quantized model's provenance. This is the torchao case: `int8_weight_only` and the other weight-only recipes rewrite `nn.Linear` only, so a CNN came back with its head in INT8 and every convolution in floating point. The message names the backend, the convolutions left behind and the backends that do rewrite convolutions (`'pt2e'`, `'x86'`); a single convolution (a patch embedding) is not a convolutional model and passes, and a per-layer `weight_bits` dict names its layers itself and is judged by that
- `Pruner` now refuses a model none of whose parameters require gradients (`No parameter requires grad: call model.requires_grad_(True) before pruning.`) instead of pruning nothing: the dependency graph torch-pruning traces needs gradients, so a frozen checkpoint used to come back untouched and silently reported as pruned
- `export_qdq(opset_version=...)` now raises `ValueError` when the graph it produced does not declare the opset that was asked for **and cannot be rewritten to it** (see the enhancement below), instead of returning a file at a different opset. `torch.onnx` exports at the exporter's own opset and down-converts afterwards; when the ONNX version converter cannot rewrite an operator it keeps the original opset and says so only in a log line. The error names both opsets, and nothing is kept on disk — not the graph, and not the external-data file it may reference. A graph that declares no opset at all for the default ONNX domain is refused with its own message rather than that one. The default (`18`) is unaffected
- A per-layer `weight_bits` dict naming a layer the backend does not quantize now raises `ValueError` instead of being silently ignored. On the legacy backends the names it accepts are the module types their default qconfig mapping rewrites (read from torch, so it tracks the installed version) plus any module containing one; `nn.Embedding`, `nn.EmbeddingBag`, `nn.LSTM`, `nn.GRU` and `nn.RNN` are not among them — the default flow leaves them in floating point. On `backend='torchao'` the names it accepts are the `nn.Linear` layers torchao itself selects, which excludes `MultiheadAttention.out_proj`
- A per-layer `weight_bits` dict that would leave *every* layer the backend rewrites in floating point now raises `ValueError`: it used to hand back an unquantized model carrying a quantized model's provenance
- A per-layer `weight_bits` dict asking for `8` inside a module the same dict leaves at `16` now raises `ValueError`: the FX flow honors the outer `16`, so the `8` could never be applied
- `Quantizer(method='dynamic', weight_bits={...})` now raises `ValueError`. `quantize_dynamic` rewrites every eligible layer off a type list and reads no per-module configuration, so the dict was accepted, ignored, and then recorded as provenance. `method='static'` and `method='qat'` honor one
- `backend='torchao'` now refuses a model whose only `nn.Linear` layers are ones torchao skips (such as a bare `MultiheadAttention`), which used to be quantized into zero layers and tagged as quantized
- `export_qdq` refuses an FX-quantized model, which carries a spec it cannot write faithfully; it used to emit a non-portable graph. On the pt2e path a capture failure raises naming the operator instead of falling back to float training, and a ragged dataloader (mixed batch sizes) is refused up front. The FX branch keeps its historical print-and-restore behavior
- A caller-supplied `qconfig_mapping` combined with the grammar arguments or with `use_per_tensor` now raises, instead of silently honoring one and dropping the other

### Enhancements
- `QuantSpec` gained `engine`: the process-global `torch.backends.quantized.engine` that was in force while the conversion ran, so `as_dict()` carries one more key. `Quantizer` sets that global for the block that converts and restores it afterwards, but the quantized kernels read it when the model *runs*, long after — a model that does not carry the engine it was built for cannot say which kernels it expects. It is the backend's name on the legacy FX and dynamic paths (`QuantizeCallback` included, whose FX conversion now runs under the engine like the rest), and `None` on `pt2e` and `torchao`, which no quantized engine governs. Old pickles keep loading
- `QDQStats` (and `qdq_stats`) gained `n_uint8`: the number of nodes whose zero-point is an explicit `uint8` constant. It is 0 on every file the default export produces, and `n_nonzero_zero_point` counts the same nodes on a uint8 file, since 128 is not zero
- `QDQStats` (and `qdq_stats`) gained `n_unquantized_conv_add`: the number of `Add` inputs the file reads from a `Conv` with no Q/DQ pair on the way — directly, or through that convolution's own single-consumer activation, which is the same partition the annotation-time pass matched. It is 0 on every graph the default placement produces, and it is what the `qdq_placement` post-condition reads. `QuantSpec` gained `qdq_placement` and `PrecisionCell` gained `qdq_placements`, so both `as_dict()` views carry one more key
- `verify_qdq` warns when the parity check is vacuous: a reference model that predicts one class for every input agrees with any graph at 1.0, whatever that graph computes
- `export_qdq(opset_version=17)` now produces an opset-17 file instead of raising. The dynamo exporter emits opset 18 and the ONNX version converter cannot bring a QDQ graph back down: opset 18 moved `ReduceMean`'s `axes` from an attribute to an input, and the converter asserts on the attribute a freshly exported graph does not have. `export_qdq` moves the axes back itself — values unchanged, in order — and drops the constant that fed them, so the file a parser limited to opset 17 rejected now parses. The rewrite is not taken on trust: the file that was written is read back by `onnx.checker` at the opset it now declares, and built and run by ONNX Runtime, output-for-output identical to the graph as produced, before it replaces it. A `ReduceMean` whose axes are computed while the graph runs, or any operator that genuinely needs the newer opset, is still refused with a message naming it, and nothing is kept on disk. Checking a lowered graph means running it, so that path needs `onnxruntime`; the default (`18`) is byte-for-byte unaffected and needs nothing new. Expect a logged traceback on the way: `torch.onnx` runs the ONNX version converter before `export_qdq` sees the graph, and the converter reports its own failure. That log is expected and is not the outcome — and on the day the rewrite is refused too, it is the first diagnostic to read
- The `#| hide` test cells moved out of the API notebooks into `nbs/tests/test_<module>.ipynb`, one notebook per API page, so a page reads as documentation and its tests read as tests. The 72 cells moved unchanged — 974 assertion calls and 19 `#| slow` cells before and after — each test notebook opens with a title and one imports cell naming the public and private symbols it uses, every API page ends its See Also with a pointer to its test notebook, and `nbs/_quarto.yml` excludes `tests/**` from rendering. The library is byte-identical across the move, `_modidx.py` included
- The quantizer tests read one resolver table instead of nine `_resolve_spec` facts duplicated from the precision tests, and the two toy models they share live in a single fixtures cell; the assertion count is unchanged
- Two `verify_qdq` argmax assertions in the quantizer tests were vacuous — the untrained reference predicted a single class for every input, so agreement was 1.0 against **any** graph — and a third had never executed, because `nbs/export/onnx_exporter.ipynb` carried `skip_exec: true` from its first commit. The reference now gets a deterministically spread classification head, prediction diversity is asserted before agreement, a foreign-graph negative control bounds the other side, and the exporter notebook runs in the default suite with every onnx use behind the existing availability guards
- Behavior-neutral simplification of the exporter, the quantizer and the sensitivity analyzer, with no signature, error text or result change: the eight refusal sites that repeated "discard the produced graph, then raise" go through one `_refusal()` helper that discards the file and returns the exception, so each site keeps its own chaining and every raise message is byte-identical; the analyzer's four fake-quantize helpers collapsed into one, `analyze()` dispatches to three single-purpose probes, and one context manager installs and releases the sparsifier buffers and activation hooks, which leaked when `eval_fn` raised mid-loop. Thirty-four multi-line rationale comment blocks left the library for the notebook prose. The sensitivity module has since moved out of fasterai (see Breaking Changes)
- CI pins `plum-dispatch<2.10` through `.github/constraints.txt`: 2.10.0 made `Function.__doc__` read-only, and fastcore writes it on the dispatched `encodes` of every `Transform` at import time, so `from fastai.vision.all import *` raised `AttributeError` on 10 of the 21 notebooks the suite ran then. The pin is CI-only; the reason and the removal condition are in the file
- Notebook cell sources are stored in the line-array form current nbdev writes, so `nbdev_clean` is idempotent on a fresh checkout and the clean-checkout gate no longer fails on every branch. Format only: notebook content is byte-identical

### Bug Fixes
- `QuantizeCallback` rebuilds the optimizer on the prepared model by parameter identity when the Learner's splitter cannot index it. Every fastai vision splitter indexes the model, which a `GraphModule` does not support, so `create_opt()` failed for every `vision_learner` on the FX and pt2e paths alike and the callback warned that it was keeping the optimizer the fit had built — noise on the most common Learner, since the prepared model's parameters are the same objects and the training was in fact correct. The rebuild now regroups by identity and keeps the old groups and their order, the discriminative learning rates and `frozen_idx`; parameters the preparation adds, the learnable fake-quant scales, join the last group and train at the head's rate, and parameters that were never trainable stay out, so a learnable fake-quant `qconfig_mapping` with a splitter, which used to fail outright, now trains. The FX path also no longer swallows a rebind failure: it caught every exception around preparation, swap and rebind and continued on the float model, so a fit could finish in floating point, announced as QAT and carrying no quantization spec. The `try` now covers the preparation only, the guard that refuses a splitter leaving parameters untrained runs on both routes rather than being one of the swallowed errors, and the recovery after a failed preparation no longer leaves the optimizer bound to the copy it just discarded
- `BN_Folder` now flushes subnormal folded parameters to zero, in float32 and float64 only. Folding a model whose channels the sparsifier emptied writes subnormal values into the folded convolution's bias — for a dead channel the fold reduces to the BatchNorm `beta` bit for bit, and training had driven those betas below the smallest normal float32 — and the convolutions that consume them then receive subnormal inputs, which x86 computes slowly; `torch.set_flush_denormal(True)` does not help, since it does not reach the intra-op threads. This is the state the documented recipe leaves a model in: sparsify, prune, fold. It was found while restoring the walkthrough, where the folded model ran about five times slower than the pruned model it came from (measured on one sparsified VGG16, CPU batch 1, three repeats on one machine, the fold the only variable). A float32 value below the smallest normal contributes nothing a float32 output can carry: on that artifact the two folds differ in 400 bias entries and their logits are bit-identical. Half precision is left on the plain formula, where the threshold is large enough that flushing would be a real perturbation with no stall to remove
- Importing `fasterai.quantize.quantizer` no longer changes torch's process-global state. The module ran a torchao INT4 kernel probe at import scope, and torchao's `quantize_` calls `recommended_inductor_config_setter()`, which sets `torch.set_float32_matmul_precision('high')`, `torch.backends.cuda.matmul.allow_tf32 = True` and five `torch._inductor.config` flags and never restores them — so a user who never asked for torchao had that probe run under their import, which changes float32 matmul numerics for the rest of the process. The probe is now lazy and memoized (`_int4_config()`, run on the first INT4 request or when the available recipes have to be listed), so module import runs no torch kernel, and both the probe and `Quantizer(backend='torchao')`'s own `quantize_` call run under `_kept_torch_settings()`, which snapshots those settings and restores them in a `finally`. A probe that fails is cached as "no INT4" for the process, which yields a refusal, never a silent pass
- `Quantizer(backend='pt2e', method='static')` observed activations with a non-clipping `MinMaxObserver` on a per-tensor symmetric int8 grid, so the extreme of the calibration range set the quantization step for the whole tensor. Torchvision EfficientNet-B0 (`IMAGENET1K_V1` weights) went from 85.63 % to 2.11 % top-1 on the Imagenette validation split (n = 3925), on every calibration draw tried. Activations are now observed with `HistogramObserver`, which is what torch's own symmetric preset builds; the activation grid is unchanged, so the exported QDQ graph still carries zero-point 0 everywhere. This removes the collapse; it does not restore the model: on the 200-image set the new test uses, the quantized model reads 32.00 % top-1 against its FP32 parent's 73.00 %, and the symmetric qscheme still costs against torch's affine preset, which is a separate decision because affine breaks the zero-point-0 guarantee. Calibration is slower with the histogram observer than with the `MinMaxObserver` it replaces
- `Sparsifier.save_model` works again: `import copy` was missing, and the saved buffers were non-leaf clones `deepcopy` refused. `SparsifyCallback(save_tickets=True)` is covered by a `#| slow` test
- `Pruner(example_inputs=...)` now traces a tensor subclass (a fastai `TensorImage`) as a plain tensor: the subclass broke the dependency trace, and the clone escapes inference mode
- `Quantizer(backend='torchao', verbose=True)` reported "quantized 0 layers" on every model: it probed a `weight.layout_type` attribute torchao no longer defines. It now reads the class of the weight
- `export_qdq` now writes the optional `kernel_shape` attribute on every `Conv` node, resolving each node's weight back through the `DequantizeLinear` that feeds it. The dynamo exporter omits the attribute, and a QDQ graph hands the weight over as a tensor rather than as an initializer, so an ONNX parser that reads spatial dims off initializers only (TensorRT's among them) had nothing to read and rejected the graph. The edit is spec-legal and semantics-preserving: strip the attributes back off and ONNX Runtime returns byte-identical logits, over an unchanged `qdq_stats`. Only `Conv` is patched; `ConvTranspose` and the pooling operators are untouched

## 0.3.3

### Bug Fixes
- `PruneCallback` now accepts a per-layer `dict` for `pruning_ratio` (matching `Pruner`); previously raised `TypeError: '>' not supported between instances of 'dict' and 'int'` (#39)
- Sensitivity analysis pruning mode now measures each layer by applying its exact per-layer target `{name: level}` — the same operation `Pruner`/`PruneCallback` perform — so the reported Δ faithfully predicts a real prune. Fixes residual/skip-coupled layers (ResNet stem conv, block `conv2`, `downsample`) being falsely ranked "Most Robust" with Δ=0 because they could not be pruned in isolation (#40)

### Enhancements
- Sensitivity analysis: coupled layers now share a `group_id` (and Δ); layers that cannot be pruned independently (output `Linear`, attention) are marked `prunable=False` and surfaced separately rather than ranked; `analyze(layer_types=...)` restricts the analysis to chosen module types (accepts a single type or a tuple); internal `Pruner` notices are silenced during analysis

### Metadata
- Corrected `requires-python` to `>=3.10` (the codebase uses `dataclass(slots=True)`)
